# Project Requirements（プロジェクト全体要件）: 共創マッチングプラットフォーム

> 人間レビュー済みのプロジェクト全体要件。プロジェクト全体の目的・範囲・要求と対応状況を管理する。機能ごとの詳細要求は、全体要件とconstitutionのレビュー後に `docs/specs/` で定義する。

## Purpose and users（目的と利用者）

自組織の課題や不足能力を十分に言語化できていない相談者が、AIとの対話と自身の確認を通じて課題と共創の可能性を整理し、適切な相手候補と評価根拠を検討できるようにする。相談者が入力した内容を起点に課題を整理する。確認できていない情報は未確認として扱い、AIが事実を補って断定しない。AIは質問、整理、説明を支援し、相談者の事実確認や候補との協業判断を代行しない。

- **相談者**: 企業・大学・自治体・専門家など、自組織の課題と共創機会を整理したい人。初期検証では運営者が相談者役を務める場合もある。
- **運営者**: 初期体験の評価、候補情報の品質と公開可否、相談・評価の再現性を確認する人。
- **候補組織・専門家**: 共創候補の情報提供やルール評価に関わる人。自ら登録・管理する機能は後続段階で扱う。

業務上の根拠は、参照先 `../ai-matching-platform` の `docs/project-context.md`、`docs/ai-design.md`、`docs/domain-model.md`、`docs/matching-design.md` と、[初期体験の移行草案](drafts/initial-demo-experience/requirements.md)・[採用判断の比較表](drafts/initial-demo-experience/legacy-comparison.md)に置く。共創パートナーシップの観点は [ISO 56003:2019 の公開要約](https://www.iso.org/standard/68929.html)を参照する。5カテゴリ・13項目は参照先の対話設計であり、ISOがその数を規定しているという意味ではない。規格本文の全条項への適合や認証は主張しない。

## End-to-end flow and boundaries（全体の業務フローと範囲）

1. **段階1：相談と課題の明確化** — 相談者の入力を起点に、目的・背景、保有能力・資源、不足能力、相手への期待、条件・制約を聞き取る。5カテゴリ・13項目の確認状況に応じて不足情報を尋ね、共創仮説を提示する。相談者が仮説と課題プロフィールを確認・修正・確定する。
2. **段階2：候補評価と初期検証** — 確定した課題だけを使い、公開可能な候補と明示された制約を確認して評価する。候補の適合点・不足点・根拠・未確認事項を示し、Cloudflare上の限定されたpreviewで主要フローを検証する。候補との協業成立は保証しない。
3. **段階3：運用拡張** — 初期検証の結果を踏まえ、認証・組織管理、候補組織の調査と登録、専門家ルール管理、評価フィードバックを個別の機能別SPECで具体化する。セマンティック検索などの検索高度化は候補データ量と評価結果から採否を判断する。

段階1・2を初期版の範囲とする。ローカルは開発・自動検証環境であり、想定実行環境はCloudflareである。参照先の業務フローと責務分離を引き継ぎ、Next.js、Vercel、Neon、pgvectorの実装や実データをそのまま移植しない。面談・PoC・契約・決済の実行、法務・知財・規制上の確定判断、ISO適合宣言は初期版の対象外とする。

## Dependencies and open decisions（依存関係と未決事項）

- **順序**: FR-001〜FR-006の相談・課題確定がFR-007〜FR-009の候補評価に先行する。FR-011、NFR-002、NFR-003、NFR-005〜NFR-008は初期フロー全体の成立条件。段階3の機能は初期検証結果を受けて個別に仕様化する。
- **候補データと公開基準（FR-007、FR-013、NFR-006）**: 初期候補の入手先、出典、審査担当、更新方法、表示可能な情報を事業側で決める。設計では、その決定に基づく取得・保存方法を選ぶ。
- **相談データの保護（FR-011、NFR-002、NFR-008）**: previewの利用者範囲、保持期間、削除方法、初期段階のアクセス制御を事業・運営側で決める。Cloudflare上の保存先とセッション識別は設計で決める。
- **候補評価の受入基準（FR-008、FR-009、NFR-004）**: 候補集合、評価観点、説明の粒度、専門家による妥当性確認方法を事業側で決める。重み、同点処理、検索方式は設計で決める。
- **検索高度化（FR-008）**: 初期版の候補取得方法と、段階3でセマンティック検索を採用するかは、候補データ量と評価結果から判断する。pgvectorの採用を前提としない。
- **規格との対応（FR-002〜FR-004、NFR-006）**: 現時点の根拠はISO 56003:2019の公開要約と参照先の対話設計。規格本文との条項単位の照合が必要かは事業側で決める。
- **後続の接続範囲（FR-015）**: 候補紹介後の面談・PoC支援を将来の機能に含めるかは、初期検証後に判断する。契約締結・決済の実行は今回の要求台帳に含めない。
