# PR #20のレビュー対応案

## この文書で提案すること

PR #20のレビューで指摘された、次の2つの問題への対応案です。対象のコミットは`03b267d`です。

1. 読み取れないJSONをAPIへ送ると、入力の誤りを示す400ではなく、サーバーの異常を示す500が返ります。JSONを受け付ける全APIで、400の共通エラー応答を返すようにします。
2. 同じローカルD1データベースを使うE2Eテストを同時に実行すると、保存件数の確認やデータベースへのアクセスが競合します。テストを1つずつ実行するようにします。

今回は対応案を文書にまとめ、検証結果を報告するところまでで止めます。コードの修正、GitHubへの投稿、マージ、デプロイ、F001のT006以降の作業は行いません。

この文書は承認前の案です。`docs/specs/`にあるレビュー済みの正式な仕様書は変更しません。正式な仕様書へ反映する手順には、まだ決まっていない点があります。詳しくは末尾の「正式な仕様書へ反映する前に決めること」に記載しています。

## 確認済みの問題と対応方針

### 1. 読み取れないJSONに500が返る

[不正JSONについてのレビュー](https://github.com/yoshikatsu-shimizu-16/open-inovation-matching-platform/pull/20#discussion_r4144688890)では、JSONの読み取りに失敗したときのエラー処理が指摘されました。

Honoのvalidatorは、callbackを呼ぶ前にJSONを読み取ります。読み取りに失敗すると、HTTPステータス400の`HTTPException`を投げます。現在の共通エラー処理`app.onError`は、この例外を500に変換してしまいます。

構文が間違っているJSON、途中で途切れたJSON、本文が空のリクエストで、いずれも`500 INTERNAL_ERROR`が返ることを再現済みです。

ユーザーは、相談APIだけを直すのではなく、全APIの共通エラー処理を直す方針を選択しました。

### 2. 同時に実行したE2Eテストが競合する

[並列E2Eについてのレビュー](https://github.com/yoshikatsu-shimizu-16/open-inovation-matching-platform/pull/20#discussion_r4144688905)では、保存件数を確認するテストの実行中に、正常系のテストがデータを保存する可能性が指摘されました。

また、作業終了時の検証を行うStop Hookでも問題が起きました。5つのworkerでテストを実行したところ、ローカルD1への問い合わせで`SQLITE_BUSY`と`SQLITE_BUSY_SNAPSHOT`が発生しました。

`CI=true npm run harness:verify`でworkerを1つにした検証は、終了コード0で完了しました。E2Eテスト5件も成功しています。ただし、これは1回だけの結果です。恒久的な修正後に繰り返し検証する作業は、まだ行っていません。

## 仕様書に追加・補足する内容

### F001-consultation-startの変更案

上位要件との対応は、既存のFR-001、NFR-001、NFR-002、NFR-005を維持します。新しい機能の一連の流れや、画面への要求は追加しません。

#### 追加する要求REQ-009

相談開始APIへ、`Content-Type: application/json`を指定して次のいずれかの本文を送った場合を対象とします。

- 構文が間違っていて読み取れないJSON
- 途中で途切れたJSON
- 空の本文

この場合、システムはHTTPステータス400と、次の応答を返します。

```json
{ "error": { "code": "INVALID_REQUEST", "message": "Invalid request body." } }
```

相談状態は作成せず、repositoryの保存処理も呼びません。

#### 追加する受入条件

以下をすべて満たしたことを確認します。

- 上記3種類の本文を400で拒否し、保存処理を呼ばない。Worker上で実行した場合も同じ応答を返す。
- 正常な相談開始では引き続き201を返す。空白だけの本文に対する`INVALID_CONSULTATION_CONTENT`、既存の入力チェックの応答、想定外の例外に対する500も維持する。
- 応答に相談本文、スタック情報、SQLなどの内部情報を含めない。
- 同じローカルD1を使うE2Eテストで、正常な入力は保存され、空白だけの入力は保存されないことを確認できる。

REQ-009は、FR-001の相談開始時の処理と、NFR-002の公開情報の保護に対応します。また、REQ-008の検証条件として、共有するローカルD1へのテストからのアクセスを1つずつ順番に行います。

### hono-backend-boilerplateの変更案

REQ-006に、次の内容を補足します。

JSONを受け付ける全APIで、JSONの読み取り失敗によるHTTP 400の例外を、共通の`400 INVALID_REQUEST`応答に変換します。公開する`message`は`Invalid request body.`に固定し、例外の本文は公開しません。

既存の`ApiError`と`DomainError`の`code`と`message`、対象が見つからない場合の応答、想定外の例外への応答は変更しません。

対象となる既存APIは、`POST /api/consultations`、`POST /api/tasks`、`PATCH /api/tasks/:id`です。リクエストと正常応答の型、データベースの構造は変更しません。

## 仕様のレビュー後に、設計とタスクへ反映する方針

以下は、後続の設計書とタスク一覧を改訂するときに引き継ぐ方針です。今回、コードを変更する指示ではありません。

### 共通エラー処理

`backend/src/app.ts`の`app.onError`で、HTTPステータス400の`HTTPException`を共通応答へ変換します。この処理は、既存の`ApiError`と`DomainError`の処理より後、汎用的な500の処理より前に置きます。

例外の`message`を文字列で比較する方法は使いません。また、すべての`SyntaxError`を400に変換することもしません。400以外の`HTTPException`には今回の変換を適用せず、既存のエラー応答の仕様を維持します。

### E2Eの実行設定

Playwrightは、ローカルでもCIでも`workers: 1`、`fullyParallel: false`に設定します。同じデータを保持するローカルD1を共有する構成は維持します。空白入力のテストで、保存されたデータの全件数を比較する方法も変えません。

### 修正の確認方法

実装前に問題を再現するテストを追加し、現状では失敗することを確認します。修正後は、結合テストでrepositoryの保存処理が呼ばれないことを確認します。Worker上では、400が返り、データが保存されないことを確認します。E2Eにも不正JSONの代表的なケースを追加します。

あわせて、正常系、既存の入力チェック、404、想定外の例外に対する500が、修正後も変わらないことを検証します。

E2E全体は、失敗時の再試行を使わず、workerを1つにして3回連続で実行します。データベースのロックが引き続き起きる場合は、完了とは扱いません。Wrangler devとD1へ問い合わせるプロセスの競合を再調査します。

## 正式な仕様書へ反映する前に決めること

R002で、正式な仕様書を再レビューする手順がまだ決まっていません。

現在のHarnessは、requirementsが承認待ちの`pending`であり、すでにdesign/tasksがある状態を、工程の順序に反するものとして拒否します。そのため、レビュー済みのrequirementsを`pending`へ戻すだけでは検証に失敗します。今回はこの問題を避けるため、変更案を正式な仕様書とは別の下書きに記録しています。

正式な仕様書を削除・移動したり、レビュー状態の記録を偽ったり、Harnessの条件を緩めたりして回避することはしません。Harnessやレビュー条件は変更せず、手順を人間と決めるまで正式な仕様書の改訂と実装には進みません。
