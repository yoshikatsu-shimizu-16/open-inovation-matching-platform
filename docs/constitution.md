# Project Constitution: 共創マッチングプラットフォーム

> プロジェクト全体要件の人間レビューを受けて作成し、PR #3 で人間レビュー済みの共通原則。機能要求と受入条件の正本は `docs/project-requirements.md`、機能別の契約は `docs/specs/<feature>/` に置く。

## Purpose

相談者の課題整理から候補評価まで、機能や実装領域をまたいで守る判断基準を定める。各原則は、後続の仕様・設計・実装・検証で具体化する。

## Principles

- **`P-001` 相談者の入力を事実の起点にする。** AIは質問と整理を支援するが、相談者が示していない事実を補完して断定しない。回答できない内容は未確認として保持し、AIの推測と確認済みの事実を区別する。
- **`P-002` 人の確認を状態の境界にする。** 共創仮説と課題プロフィールは相談者が確認・修正できる形で提示する。候補評価には相談者が明示的に確定した課題だけを渡し、AIの出力や下書きだけで確定状態へ進めない。協業の可否、法務・知財・規制上の判断も人が行う。
- **`P-003` AI出力を検証可能な入力として扱う。** AIが生成した内容は定義済みの契約で検証し、不正な出力を確定課題や候補結果へ混入させない。利用した対話ルールと情報源の版を追跡できるようにし、根拠と未確認事項を結果から識別できるようにする。
- **`P-004` 候補評価の判断根拠を再現できるようにする。** 候補の公開状態と明示された制約を評価前に確認する。順位と内訳は版が特定された課題・候補・評価規則から再計算可能な処理で決め、AIに最終順位を委ねない。適合点と不足点を示し、共創可能性は検討仮説として伝える。
- **`P-005` 相談と候補の情報を利用範囲に応じて保護する。** 認証情報をブラウザ、コード、仕様へ埋め込まず、相談内容や未公開知財の本文を一般ログへ無制限に出さない。初期previewでも利用者と相談単位のアクセス境界を設け、公開不可または未審査の候補を相談者向け結果に含めない。保持・削除・公開の具体的な条件は、運営上の決定を受けて機能別SPECで定める。
- **`P-006` 確認済みの作業を障害時にも保つ。** AI処理、候補の取得、候補なしの状態を区別して扱い、失敗時に相談者の確認済み入力を失わせない。再試行や課題の見直しへ戻る経路を設ける。
- **`P-007` 実行環境と責務の境界を守る。** 初期版の主要フローは React/Vite の `frontend/`、Hono の `backend/`、Cloudflare Workers の `infrastructure/` を基準に設計する。ローカルは開発・検証に用い、想定実行環境は Cloudflare preview とする。UI、業務判断、保存・実行設定の責務を分け、領域間の契約を実装前に仕様へ記す。
- **`P-008` 仕様と検証根拠に従って変更する。** 利用者に見える振る舞い、API、データ契約を変更する前に、対応する FR/NFR と機能別SPECを更新し、人間レビューの境界を守る。完了は自動検証と必要な人の確認の根拠で判断する。主要フローは外部AIの実応答に依存せず正常系と障害系を検証する。
- **`P-009` 初期検証の結果に応じて拡張する。** 初期版は相談・課題確定と候補評価に集中する。認証・組織管理、候補登録、専門家ルール管理、フィードバック、検索高度化は、初期検証と別途の仕様化を経て採否を決める。参照先システムの実装方式や実データを自動的に移植しない。

## Change process

原則の追加・変更・廃止では、理由、影響する FR/NFR と機能別SPEC、改訂日、関係する仕様の再レビュー要否を変更履歴に記録し、人間レビューを受ける。原則IDは別の意味に再利用しない。要件側で未決の事業判断を、この文書だけで確定しない。

## Non-goals

- 全体の機能・非機能要求と個別の受入条件（`docs/project-requirements.md`）
- 機能別要求・設計・タスク（`docs/specs/<feature>/`）
- 評価重み、アクセス制御方式、データ保持期間など、後続の事業判断と設計で定める詳細
